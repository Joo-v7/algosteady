# 아키텍처

## 서비스 목표

사용자가 자료구조 또는 알고리즘을 직접 구현하고, 공개 예시 실행과 기준별 테스트로 동작을 확인한다. 항목 선택, 구현, 실행, 채점, 수정, 기록 확인을 하나의 훈련 흐름으로 제공한다.

## 시스템 구성

```text
브라우저: React + Monaco Editor
    │ HTTP /api
    ▼
Spring Boot
    ├── 콘텐츠 조회
    ├── 초안 및 제출 관리 ── PostgreSQL
    └── 채점 작업 관리
             │ 단일 작업 큐
             ▼
       Docker 실행 컨테이너
             ├── C17 컴파일
             ├── 테스트별 실행
             └── 출력 및 종료 결과 수집
```

브라우저는 화면과 편집을 담당하고, 백엔드는 기록과 작업을 관리한다. 제출 코드는 작업용 컨테이너에서 실행한다.

### 목록 화면

자료구조와 알고리즘 분류별로 과제를 표시한다. 과제별 지원 언어, 미시도, 시도 중, 통과 상태와 최근 작성 시간을 보여준다. 훈련 횟수는 제한하지 않는다.

### 과제 화면

과제 화면은 `학습`과 `구현 훈련` 탭으로 구성한다. 처음 과제를 열면 학습 탭을 표시한다. 반복 훈련을 위해 목록에서 구현 훈련 탭으로 바로 진입할 수 있으며 학습 완료를 강제하지 않는다.

#### 학습 탭

개념, 구조, 연산 과정, 구현 코드 순서로 학습한다.

- 개념: 자료구조 또는 알고리즘의 목적과 핵심 원리.
- 구조: 자료형, 필드, 변수와 상태를 그림 및 설명으로 표시.
- 연산 과정: 입력에 따라 값과 상태가 변하는 순서를 예시로 표시.
- 구현 코드: 함수별 코드를 펼쳐서 보고 설명과 비교.
- 훈련 시작: 같은 과제와 언어의 구현 훈련 탭으로 이동.

개념과 선언만 보는 것은 기준 코드 열람으로 처리하지 않는다. 완성된 함수 구현을 펼치면 현재 훈련 회차에 기준 코드 열람 여부를 기록한다. 학습 탭에서 본 구현과 훈련 탭에서 본 기준 코드는 같은 기록 규칙을 적용한다.

#### 구현 훈련 탭

- 상단: 분류, 제목, 언어, 누적 작성 시간과 일시 정지.
- 왼쪽: 개념, 구현 규격, 코드 에디터, 공개 예시와 실행 결과.
- 오른쪽: 제출 전부터 표시하는 채점 기준과 기준별 진행 상태.
- 하단: 컴파일·실행, 채점, 기준 코드 보기.

에디터는 문법 강조와 들여쓰기를 제공하고 자동 완성은 최소화한다. 코드를 수정하면 기존 결과에 수정 전 코드의 결과임을 표시한다.

시작 코드는 필요한 헤더, 상수, 자료형과 함수 선언만 제공한다. 사용자는 함수의 정의와 본문 전체를 작성한다. 학습 탭과 구현 훈련 탭을 전환해도 작성 코드와 해당 회차의 열람 기록은 유지한다.

### 기록 화면

항목과 언어별 제출 코드, 기준별 결과, 작성 시간, 실행 시간, 기준 코드 열람 여부를 표시한다. 이전 제출을 현재 에디터로 불러올 수 있다. 재훈련은 기존 제출을 보존하면서 새 작성 시간을 시작한다.

## 백엔드 구성

기능별 패키지를 사용하고 패키지 안에서 요청 처리, 업무 처리, DB 접근을 구분한다.

| 패키지 | 책임 |
| --- | --- |
| `exercise` | 콘텐츠 등록, 목록, 상세, 기준 코드 |
| `training` | 훈련 회차, 초안, 작성 시간, 열람 기록, 제출 원본과 기록 조회 |
| `judging` | 실행 및 채점 작업 큐, 진행 상태, 기대값 비교와 결과 저장 |
| `judging.runner` | 언어별 준비, 컨테이너 실행, 출력 수집, 제한 및 정리 |
| `common` | 공통 설정, 오류 응답 등 공유 기능 |

Controller는 요청과 응답을 처리하고 Service가 업무 흐름 및 트랜잭션을 관리한다. Repository는 JPA 저장과 조회를 담당한다. API 응답은 DTO를 사용한다.

```text
com.algosteady/
├── exercise/
├── training/
├── judging/
│   └── runner/
└── common/
```

기능 안에는 필요한 controller, service, domain, repository, dto를 둔다. 사용하지 않는 패키지와 빈 클래스는 생성하지 않는다. 실행부의 내부 요청과 결과는 record로 표현하고 model에 둔다.

### 의존 방향과 데이터 소유권

의존 방향은 `training → judging → exercise`다. `exercise`는 버전별 콘텐츠를 제공한다. `training`은 제출 원본을 저장한 뒤 코드, 과제 ID, 콘텐츠 버전, 언어를 `judging`에 전달한다. `judging`은 해당 버전의 호출 코드와 테스트를 `exercise`에서 조회하며 `training`의 Entity나 Repository를 참조하지 않는다.

제출 저장과 작업 등록은 같은 DB 트랜잭션으로 처리한다. 단일 작업자는 커밋된 DB 대기 작업을 읽고 실행한다. 실행에 필요한 코드와 버전은 작업 요청에 보존하여 제출 저장소를 다시 읽지 않는다.

채점 상태와 결과는 `judging`만 저장한다. 채점이 끝나도 `training`의 제출을 갱신하지 않는다. `training`은 제출에 연결된 작업 ID로 `judging`의 조회 서비스를 호출해 원본과 결과를 합친 응답을 제공한다. 제출에 채점 상태나 결과를 중복 저장하지 않는다.

## 데이터 모델

| 데이터 | 주요 내용 |
| --- | --- |
| 훈련 항목 및 버전 (`exercise`) | 과제 ID, 콘텐츠 버전, 분류, 제목, 개념, 규격 |
| 언어별 구현 정보 (`exercise`) | 시작 코드, 기준 코드, 함수 규격 |
| 기준 및 테스트 (`exercise`) | 기준 ID, 순서, 설명, 테스트 연결, 입력과 기대 결과 |
| 훈련 회차와 초안 (`training`) | 과제와 언어, 코드, 누적 작성 시간, 열람 여부 |
| 제출 (`training`) | 제출 ID, 코드 원본, 과제와 콘텐츠 버전, 언어, 작성 시간, 열람 여부, 작업 ID |
| 작업 (`judging`) | 실행 또는 채점 종류, 실행 요청, 대기 및 실행 상태 |
| 실행 및 기준별 결과 (`judging`) | 상태, 실패 테스트, 기대값과 실제값, 오류, 실행 시간 |

콘텐츠 원본은 파일에서 관리하고 검증 후 DB에 등록한다. 같은 과제의 콘텐츠 버전은 별도로 보존한다. 제출은 평가에 사용한 버전을 참조하며 과거 제출 결과는 변경하지 않는다.

스키마는 Flyway로 생성 및 변경한다. JPA는 `ddl-auto=validate`로 검증하고 `open-in-view=false`를 사용한다.

## API

| 메서드와 경로 | 역할 |
| --- | --- |
| `GET /api/exercises` | 분류별 과제 목록과 언어별 진행 상태 |
| `GET /api/exercises/{id}?language=c` | 학습 설명, 연산 과정, 규격, 시작 코드, 공개 예시, 기준 |
| `GET /api/exercises/{id}/reference?language=c` | 기준 코드 조회와 열람 기록 |
| `GET /api/drafts/{exerciseId}/{language}` | 현재 초안 조회 |
| `PUT /api/drafts/{exerciseId}/{language}` | 코드, 작성 시간, 열람 여부 저장 |
| `POST /api/runs` | 선택한 공개 예시 실행 |
| `POST /api/submissions` | 제출 저장과 전체 채점 요청 |
| `GET /api/jobs/{id}` | 작업 진행과 기준별 결과 |
| `GET /api/submissions?exerciseId=…&language=…` | 제출 기록 목록 |
| `GET /api/submissions/{id}` | 제출 코드와 결과 상세 |

완성된 학습 코드와 기준 구현은 기준 코드 조회를 통해 제공한다. 과제 상세 응답에 완성된 구현을 포함해 미리 내려보내지 않는다.

실행과 채점 요청은 과제 ID, 콘텐츠 버전, 언어, 코드를 포함한다. 실행 요청에는 공개 예시 ID를, 채점 요청에는 작성 시간과 기준 코드 열람 여부를 추가한다.

서버는 작업 ID를 즉시 반환한다. 화면은 500ms 간격으로 상태를 조회하고 종료 상태에 도달하면 조회를 멈춘다. `컴파일·실행`은 제출을 만들지 않고 `채점`은 매번 새 제출을 만든다.

## 작업과 판정

작업 상태는 `QUEUED`, `RUNNING`, `COMPLETED`, `FAILED`로 관리한다. `COMPLETED`는 평가 처리가 끝났다는 의미이며 코드가 정답이라는 뜻은 아니다. 작업 수행 장애는 `FAILED`로 기록하고 코드의 오답과 구분한다.

기준 상태는 대기, 판정 중, 통과, 실패, 검사 불가로 관리한다. 기준에 연결된 모든 테스트가 통과하면 해당 기준이 통과한다. 실제 판정 완료 순서대로 상태를 갱신하고 독립적인 기준은 계속 검사한다.

- 컴파일 실패: 컴파일 오류를 표시하고 기능 기준은 검사 불가로 처리.
- 테스트 실패: 해당 기준을 실패로 표시하고 입력, 기대값, 실제값과 오류 제공.
- 시간 및 출력 초과: 해당 테스트의 실패 원인으로 기록.
- 실행 환경 장애: 작업 오류로 기록하고 미실행 기준은 검사 불가로 처리.
- 서버 종료로 중단된 작업: 재기동 시 중단 사실을 기록하고 자동으로 통과 처리하지 않음.

## C 실행 환경

### 실행부 구성

```text
judging/runner/
├── service/          CodeExecutionService
├── model/            ExecutionRequest, TestInput, PreparationResult,
│                     TestExecutionResult, ExecutionResult
├── language/         LanguageSpec
├── config/           RunnerProperties
└── infrastructure/   DockerContainerManager, DockerExecutionSession,
                      ProcessExecutor
```

CodeExecutionService는 언어 선택, 준비, 테스트 순서를 관리한다. LanguageSpec은 언어별 제출 및 호출 코드 파일명과 준비·실행 명령을 Java에 정의한다. 명령은 인자 목록으로 전달하고 브라우저나 콘텐츠 파일에서 실행 명령을 받지 않는다. 현재 지원 정의는 C17이다. 다른 언어도 같은 Service와 결과 모델을 사용하며 Python은 준비 단계에서 문법을 검사한다.

RunnerProperties는 이미지와 시간·출력·자원 제한을 application.properties에서 읽는다. DockerContainerManager는 임시 공간과 컨테이너를 생성한다. DockerExecutionSession은 해당 작업의 준비·실행·종료와 정리를 담당하며 AutoCloseable로 사용한다. ProcessExecutor는 호스트 명령과 출력 수집을 담당하며 Docker 관리부를 참조하지 않는다. 제한에 도달하면 세션에서 전달한 종료 처리를 호출한다.

호출 방향은 `CodeExecutionService → DockerContainerManager / DockerExecutionSession → ProcessExecutor`다. Docker 명령 응답 제한과 제출 프로그램의 실행 제한은 구분한다. 호스트의 Docker CLI 종료만으로 내부 프로그램 종료를 대신하지 않는다.

ExecutionRequest에는 언어, 제출 코드, 호출 코드, 순서가 있는 TestInput 목록을 담는다. 기대값 비교는 judging의 채점 서비스가 수행한다. ExecutionResult는 PreparationResult 하나와 TestExecutionResult 목록을 담는다. 준비 실패에도 준비 결과를 반환하며 미실행 테스트의 종료 코드와 시간만 값이 없다.

실행 서비스는 `execute(ExecutionRequest, Consumer<TestExecutionResult>)`로 호출한다. 테스트 결과가 확정될 때마다 콜백을 전달하여 채점부가 실제 완료 순서대로 판정하고 저장한다. 실행부는 DB에 접근하지 않는다. 단일 작업 실행은 judging의 작업자가 관리하며 실행 서비스는 작업마다 독립된 세션을 사용한다.

한 번에 하나의 작업을 실행한다. 제출 코드와 과제의 테스트 호출 코드를 결합해 컴파일하고, 테스트마다 새 프로세스와 자료구조 상태를 사용한다.

| --- | --- |
| 언어 | C17 |
| 플랫폼 | Apple Silicon ARM64 지원 |
| 이미지 관리 | 컴파일러 및 이미지 버전 기록, 배포 이미지 digest 고정 |
| 실행 권한 | 일반 사용자, 권한 및 capabilities 제한 |
| 네트워크 | 차단 |

| 컴파일 제한 | 30초 |
| 실행 제한 | 테스트별 2초 |
| 출력 제한 | 테스트별 stdout와 stderr 합계 1MiB |

백엔드는 Docker 제한과 별도로 시간 및 출력 제한을 감시한다. 작업별 임시 공간을 만들고 완료, 실패, 시간 초과 시 컨테이너와 임시 파일을 정리한다.

실행 시간은 테스트 프로그램 시작부터 종료까지 측정한다. 이미지 준비와 컴파일 시간은 제외한다.

현재 실행 관리 스크립트의 측정에는 timeout 시작과 관리 명령의 오버헤드가 포함된다. Docker CLI와 컨테이너 준비 시간은 포함하지 않는다. 정밀 측정 방식 개선은 실행부 구조 변경과 분리해 진행한다.

## 개발 및 배포

개발 중에는 Vite 5173, Spring Boot 8090, PostgreSQL 5432를 실행한다. Vite의 `/api` 프록시로 백엔드에 연결한다. DB 포트는 `127.0.0.1`에만 연결하고 데이터는 named volume에 보존한다.

초기 배포는 React 빌드 결과를 Spring Boot에 포함해 화면 파일과 API를 제공하는 방식으로 구성한다. 클라이언트 화면 경로는 React 진입 문서로 연결하고 `/api` 오류는 API 응답으로 유지한다. 실행 컨테이너는 API 서버와 분리한다.

`dev`에서 개발하고 검증한 변경을 `main`에 병합한다. 배포 자동화 단계에서는 `main` 병합 후 빌드, 검증, 배포를 실행한다. IDE 설정, 실제 환경변수, 설치 의존성과 빌드 결과는 Git에서 제외한다.
